The mushaf, page by page, as files you can build with

The 604 pages of the Madinah Mushaf as SVG files, one file per printed page. Each page looks exactly like the print it came from, and everything on it is a real element you can select, style and link to.

There is no SDK and no build step. Fetch a page and query it with plain DOM:

Why you would want it. Building a Quran app usually means choosing between two bad options. A page image looks right, but nothing on it can be selected, searched or linked. Text set in a font is alive, but it is not this print, and you have to rebuild the line breaks page by page so a reader still recognises the page they memorised from. These files give you both at once.

It also replaces your Quran metadata database. Most apps ship page images next to a database that says what is on them. Here that information is on the elements. Every word carries its key 2:255:4 and its rasm_uthmani text; every ayah fragment carries 2:255; every page carries its surah records, its juz, hizb, rubʿ and nisf starts, its line numbers, and every mark by name. So "ayah 2:255 is on page 42, line 3" is a CSS selector rather than a query, and because the geometry is in the same file you also get what a database cannot give you: where each of those sits on the page.

The guarantee

Every one of the 604 pages renders identically to the source artwork. Decomposing a page into ayahs, words and marks changes nothing that is drawn.

Two checks run on every page on every change, and a failure blocks the release:

  • Contour conservation — the multiset of drawn contours in the output is identical to the source. Nothing added, nothing removed, nothing duplicated. This catches what a picture cannot show, such as a mark drawn twice in the same place.
  • Raster comparison against the source artwork, so nothing has moved. Rendered 1400 px wide and re-verified at 2200 px, tolerance 24/255, with a 10 px seam allowance for anti-aliasing.

The guarantee covers the ink: what is drawn, and where. It does not cover how the ink is named — which stroke is a kasrah, which word owns which mark. That rests on separate evidence.

How the editors work every snippet is live, and yours to change

Every snippet below is editable and runs for real. The result updates as you type, Ctrl/⌘+Enter runs it immediately, and Reset restores both the snippet and an untouched copy of the page. Each editor holds its own copy of the file, so one section cannot disturb another.

A snippet runs with five things in scope, and everything else is plain DOM:

  • svg is that section's page, already parsed.
  • stage is the paper the page sits on.
  • out(html) and log(…) write to the readout beside the editor.
  • H holds the helpers this page defines: H.band, H.fold, H.crop, H.getPage and H.toRoot.
  • signal is an AbortSignal that fires when the snippet re-runs, so a listener or an observer you attach outside the page is cleaned up for you.

Read what is on the page

The file answers questions. There is no database and no SDK.

Look inside a page Fetch one file, count its words, read its viewBox.

fetch → DOMParser → querySelectorAll

A page is an ordinary SVG file with a fixed viewBox. Parse it and query it. This snippet fetches page 3 over the network for real — change the page number, or the ayah, and run it again.

Document order is reading order. Words inside a line run right to left, on all 8,820 lines of the mushaf that hold words. Don't sort by geometry: bounding boxes overlap, because a mark may legitimately be drawn over its neighbour.

Read a word Five spellings and every named mark, on one word.

data-rasm-uthmani on the page · rasm rasm_imlai search qpc in the sidecar

Every word group carries its key and its rasm_uthmani text. The other four spellings come from the page's sidecar, index/by-page/NNN.json. Every path says what kind of ink it is and, if it is a mark, which mark. The snippet installs the listener — hover the page beside it, then change what the readout reports.

Read the name off the attribute, never off the shape. fathah and kasrah are the same stroke, named by where it sits, so the outline cannot tell you which one you have. A hamzah that is a diacritic and a hamzah that is a letter of the word are identical ink too, and data-kind is what separates them.

A mark can be drawn outside its own word. The tanwin of a word-final ة floats into the gap toward the next word. Assign a mark by its enclosing group, not by nearest ink or by bounding box.

Search, and land on the ink This page or all 604 — then light up the printed word.

search on the search form

All ink is paths and there are no <text> nodes, so browser find-in-page cannot work. Search the search form instead. It ships once per page in index/by-page/NNN.json, and dev-profile pages also carry it inline as data-search. Edit the query in the snippet, or swap search for rasm and watch the hits vanish.

Searching on rasm matches almost nothing

rasm is the skeleton of the rasm_uthmani spelling, which is what the page draws. rasm_uthmani writes several long vowels as combining marks, so stripping the marks deletes those vowels outright and leaves a spelling nobody types. Measured over all 77,432 words:

ٱللَّهُ has an alef hamzat_al_wasl (U+0671) where a keyboard produces a plain alef, so rasm is ٱلله and never matches. دَرَجَٰتࣲ carries a dagger alef (U+0670), which is a mark, so the rasm is درجت with no alef at all. search is the skeleton of the modern (rasm_imlai) spelling and has neither problem. Use rasm for what it is for: matching text against the shapes actually drawn on the page.

Nothing is folded for you. That is deliberate. ا أ إ آ stay distinct, so do ى/ي and ة/ه. If your users expect a forgiving search, fold on your side and keep the stored value as written. The snippet above does the fold; delete it and see what happens.

Point at something

An ayah is several nodes, and the ink is thin. Both have a fix.

Highlight an ayah It is never one node. Select it, then paint behind it.

svg.querySelectorAll('g.ayah-fragment[data-ayah-key="2:255"]')

An ayah is emitted once per printed line, so it is several sibling nodes and there is no single node that "is" the ayah. 6,236 ayahs are emitted as 13,489 fragments; 4,455 of them have more than one. Change querySelectorAll to querySelector in the editor and watch five sixths of Ayat al-Kursi stop being highlighted, without anything throwing.

Each fragment carries data-fragment and data-ayah-fragments, and all 13,489 of them carry data-mark pointing at the id of their own medallion on the same page. No ayah spans two pages, so if you loaded the right page you will always find all N. Never use firstElementChild of one fragment to find the ayah's first word — use data-word-key order across all fragments. Deep links work on the page at the top of this document: #2:254, #2:255.

getBBox() per word, unioned per printed line

Compute the band from the words. Union the word boxes, one box per printed line the ayah occupies, and paint them behind the ink as one polygon — a single <path> with a subpath per line. No <g> inside a word carries a transform, so word.getBBox() is directly usable. The whole function is in the editor: change the padding, the colour or the ayah and it redraws.

Draw one polygon, not one rectangle per line

Arabic ink overruns its line: ل and ك reach up into the line above, ج and ي reach down. So the band for an ayah is one rectangle per printed line, and those rectangles meet or overlap.

Do not emit them as separate <rect>s. Two abutting antialiased edges do not add up to opaque, so every join shows a pale hairline and a six-line ayah reads as six stripes rather than one highlight. Make each line a subpath of a single <path>, wind them all the same direction, and overlap them vertically by a fraction of a unit. One element, one flat region, no seams.

Set fill-rule explicitly; never inherit it. nonzero makes overlapping subpaths union instead of cancel, which is why the overlap costs nothing. The page's own ink is evenodd, where overlapping contours inside one path cancel, so inheriting it turns every overlap into a hole. Set the alpha once, on the group. The highlight is a layer behind the ink rather than a colour on it, so the print stays untouched.

Make a tap in the gap land One CSS rule, and not a single pixel changes.

g.word path { stroke: transparent; pointer-events: all }

Hit-testing runs against the ink, and the ink is calligraphy: thin strokes with white space between the words, so a finger landing between two words hits nothing. One CSS rule fixes it and changes no pixel, because a transparent stroke behind the fill is still hit-tested and paints nothing. Click the line below with the halo at 0, hunt for a gap, then set HALO to 1.6 and click the same spots again.

Prefer this to the invisible per-ayah polygon that older mushaf SVGs use as a hit layer. Where two ayahs share a printed line the real boundary is jagged, because letters interleave and marks overhang, so a rectangular polygon paints part of the wrong ayah or misses ink of its own. Walking up from the word cannot be wrong, since the ayah's ink is its words. Above about 2.5 units the halos start stealing each other's gaps.

Drag across it and copy real text A selection layer over ink that has no text nodes.

one invisible <span> per g.word, over the ink

Drag over the page with the mouse, then Ctrl/⌘+C, or right-click and Copy. You get the Quranic text. The file has no <text> elements, so native selection has nothing to grab. Overlay a text layer instead: one absolutely-positioned span per word, carrying the real Unicode and painted with color: transparent on top of the word's own rendered box. PDF.js uses the same trick, it needs no library, and the ink underneath is untouched.

Five problems with a selection layer, and the fix for each

  • getBBox() is the wrong measurement. It reports a group's own user-space coordinates and ignores every transform above it, which puts line 1 near the bottom of the page. Use getBoundingClientRect() on the word and subtract the layer's own rect — it is already through the whole transform chain. Worst residual misalignment across all 127 words of page 3 is then 0.016 px.
  • Caret placement inside a span uses the fallback font's advances, which have nothing to do with the ink, so a drag starting mid-word cuts it at an arbitrary letter. Snap the range out to whole spans on mouseup. Word granularity is what a mushaf reader wants anyway.
  • Do not size a span to its LINE's box. A line group's rect includes the ascenders and descenders that overrun into its neighbours, so the bands overlap and darken. Per-word boxes look right.
  • Do not put a newline inside a span, and do not use a separate zero-size break span. The first makes that span two text lines tall, so its band spills onto the line below; the second has its newline collapsed away and never reaches the clipboard. Build the payload yourself in a copy handler instead.
  • A mousedown on already-selected text does not start a new selection. It starts a native drag-and-drop of that text, and the old selection stays frozen for the whole gesture, so the second drag appears to do nothing. It bites hardest when the user tries again, because the words under the pointer are the ones they just selected. Clear the selection on mousedown and refuse dragstart: two lines, and every drag starts fresh.
  • Give the boxes full line height, so they meet their neighbours. Otherwise a range has dead zones between the boxes, and the first and last word need deliberate aim. This card and Make a tap in the gap land, Hover a word and Three of these at once share one layer and one box size for that reason.

Build the payload yourself, and choose the spelling at copy time

The text is looked up from data-word-key rather than serialised out of the layer, so the same drag can yield different text. Quote it as the print sets it, take the modern spelling, or take the bare form to paste into a search box. Change the WHICH line in the editor, or use the selector in the toolbar.

A page image has nothing to select, and a font gives you the one spelling it was set in. Here the selection is a set of word keys, and the spelling is chosen when the user presses copy.

Test coverage. The copy event and the payload it produces are tested: a real mouse drag across a line break, the highlighted band and the copied word set agreeing at both boundaries, and the mushaf's own line break preserved as a newline. The handoff to the operating system clipboard is checked by hand, because the headless browser used here has no clipboard backing.

Three of these at once Do hover, copy and highlight fight each other? No.

one hit layer · many capabilities

A real reader runs several of these together, so here are three at once on one page: hover a word for its meaning, drag across it and copy real text, and a band behind the ayah you are on. This is the same code as Drag across it and copy real text, Hover a word and Highlight an ayah, sharing one hit layer.

Give the pointer to one layer only

There are three layers, and only the top one takes the pointer. The highlight bands sit behind the ink, the ink itself is pointer-events: none, and the per-word hit layer on top is the only thing hit-testing reaches. That layer is one element per word carrying its data-word-key, so selection, hover, tap and click all read from the same source instead of stacking competing overlays.

The cursor is the one thing the layers cannot share: selection wants cursor: text and a tooltip target wants cursor: help. Pick one per surface. Everything else composes.

One word at a time

Every word is an element, so anything can be driven per word.

Reveal the page word by word Grey the page and bring it in on a schedule.

g.word { fill: … } — one property, one word

Every word on the page starts light grey. The reading position is full ink, and it advances, each word fading in as it is reached. This is what a memorisation prompt, a reading-along view and a "you are here" indicator all reduce to. Once words are addressable, all three are one property away. A page image cannot do it at all, because recolouring one word at a time needs per-word ink.

Set the colour on the group, not on 1,000 paths

Every ink path ships fill="#231f20" as a presentation attribute, so a <g>'s inherited fill will not reach it on its own. A CSS rule beats a presentation attribute, so one rule hands each path back to its group. Recolouring a whole word is then one property on one element per tick, whatever the word is made of.

Page 42 holds 147 words over 1,061 paths, and the transition is on fill. It stays smooth because a tick touches one element rather than a thousand, and the browser does the interpolation. If you need it cheaper, transition opacity on the group instead.

Swap the schedule for real timings

A schedule(i) function returns the millisecond at which word i lights. Here it is a constant tempo. Pass an array of per-word start times from a recitation aligner instead and the same loop follows a recitation.

Nothing here is synced to a recitation. These files carry no audio and no word timings, and this animation is a metronome. It is worth showing because data-word-key is surah:ayah:word, the same key word-level timing datasets are published under, so the join needs no mapping table.

Word order is document order: right to left within a printed line, lines top to bottom, on all 8,820 lines of the mushaf that hold words. The loop below never sorts by geometry.

Follow a recitation Word-level timings against word-level elements.

word_number → the third part of data-word-key

The same grey-to-ink mechanism as Reveal the page word by word, with the tempo replaced by real per-word timings. Press play and the highlight follows the recitation, because quran.com publishes word timings under the same key this page uses: word_number is 1-based within the ayah, which is the third component of data-word-key. No mapping table, no alignment step.

Check the word counts before you trust the numbering

Two decompositions can disagree about how many words an ayah has. On page 254, 13:37 is 19 words to quran.com and 20 in this print, which sets بَعْدَ مَا as two words. Consume the timings blindly and the highlight drifts by one word to the end of that ayah, which looks like a geometry bug and is worse than no highlight at all.

Compare the highest word_number against your own count for that ayah, and highlight the ayah whole when they differ. Across pages 1, 3, 42, 582 and 604 the counts agree exactly on 67 ayahs; page 254 has the one mismatch. The lab prints the check either way.

Hover a word, see what it means A gloss keyed by data-word-key.

data-word-key === quran.com's word key

Move the pointer over any word on the page and its meaning appears. Tap works on touch, and the words are focusable so Tab and the arrow keys do too. data-word-key is surah:ayah:word, 1-based — the same key the quran.com API, word-by-word translation sets, morphology data and recitation timings already use, so a 5 KB file of glosses joins to this ink with no mapping table.

The gloss shown here is an example, not a feature. It is word-by-word translation English from quran.com, chosen because it is open data anyone can check. Put a tafsir, a grammar tag, a vocabulary card or any per-word data you already have in its place and the same three lines still run. These files ship no translations.

Put the hit areas inside the SVG, as transparent <rect> elements, one per word. Attaching to the paths makes the tooltip flicker as the pointer crosses the gaps between letters. If you combine this with the HTML text layer in Drag across it and copy real text, that layer sits above the SVG and swallows these events, so decide which one owns pointer-events rather than stacking both.

The word-by-word translation and transliteration used here come from quran.com. They are third-party data, shipped separately from the SVGs and attributed to their source. Translations, tafsir and audio are not part of this corpus either, and all of them join on the same key.

Hide the vowel marks, not every mark

The 9 vowel marks carry diacritic in data-mark-family: fathah, kasrah, dammah, sukun, shaddah, maddah and the 3 tanwin. Hiding exactly those is one selector, and everything else stays where it belongs. That is the second specimen above, and it is what a reader mode or a memorisation aid wants.

Do not hide every mark. Diacritics, letter dots and waqf signs are all data-kind="mark" paths, so path[data-kind="mark"]{display:none} takes all three away at once — the third specimen above, and it is not undiacritised text. The dots are the letters: ب ت ث differ by nothing else, so hiding them destroys letter identity. The waqf signs carry recitation information rather than vowelling.

data-mark-family is a space-separated token list, like class. A mark can belong to more than one family: the 3 tanwin are vowel marks and they are also the tanwin, so they carry data-mark-family="diacritic tanwin" and answer to both names. Match it with ~=, never =:

An exact-match selector is wrong rather than merely strict. It looks like it works, because it still matches the 6 single-family marks, and it drops the 3 tanwin without an error. Every selector on this page uses ~=.

svg path { fill: … }

Every ink path in the whole mushaf is the same colour, #231f20, so one rule changes all of it. That gives you a real dark mode, a high-contrast print sheet, or a page that matches your own palette. None of it touches the geometry.

Set the fill; do not rasterise the page and filter it. A CSS filter: invert() over an image gives you grey paper and muddy ink, and it fights every other colour on the page. Here the ink and the ground are independent.

g.ayah-mark > path[data-kind="ayah_mark_ornament" | "ayah_number"]

The medallion at the end of an ayah is <g class="ayah-mark" id="mk-2-255"> holding two paths: the ornament ring, and the printed numeral. They are separate elements, so you can restyle the ring without touching the number. Recolour the ring on its own, hide it and keep the numeral, scale the whole medallion, replace the ring with a shape of your own, or drop the medallions entirely for a plain reading view.

The ring outlines are not part of this page. The designs in the picker are fetched at runtime from quranpedia/ayah-marks, which traces them from 20 type families: 15 from Google Fonts and 5 from fonts.quran.ws. They carry those families' licences, which differ from one another, and every marker names its own sources in that repository's collection.json. Read it before you redistribute anything. Neither this page nor the library ships an outline or states any licence terms. If the fetch fails the section says so and the printed rings stay.

The numeral is the print's own drawing of the number rather than a font rendering, so it stays exactly as printed however you dress the ring around it. Pages 1 and 2 also carry 12 decorative rosettes with no ayah at all, the frame of the opening spread, so select g.ayah-mark[data-ayah-key] when you mean the real ones.

A library, if you want one

Every section above has a plain JS / library switch in its toolbar. Both versions are real, both are editable, both run, and both produce the same result. Plain JS is the default, because these are ordinary SVG files and need no library at all.

What the library saves you is the traps, not the typing. It has the callouts on this page built in and tested: that an ayah is several nodes, that getBBox() reports the wrong position, that a band must be one path, that a word's trailing ink is drawn into the following gap, and that data-mark-family is a token list.

Getting it

Zero dependencies, no build step, no framework. An ES module, or a <script> tag with everything on one global — which is what this page loads, the first time you press library in any toolbar.

core.mjs imports nothing, and everything else is a free function taking a page — attachSelection(page, …), mask(page, …) — so a bundler can drop what you do not use.

Three rules the library keeps everywhere

  • Nothing mutates a page you did not hand it. MushafPage.load() and page.clone() give you a page you own. new MushafPage(el) wraps an element without cloning, so a later call changes your element, which is what every library snippet on this page relies on.
  • Every mutating call returns a handle with .remove() that undoes exactly what it did and nothing else. There is no global reset.
  • The shared hit layer is reference counted. Hover, click and selection each take a reference and give it back, so the layer is built once and torn down when the last holder releases it. That is what lets Three of these at once run three capabilities over one page without any of them knowing about the others.

Two places the library is stricter than these snippets

It never selects on data-mark-family. It resolves a family to data-mark names through an embedded taxonomy, so a build that changes the attribute's vocabulary cannot break your code.

Its hit testing is nearest-with-direction: a point in the gap between two words goes to the preceding one, because in this print a word's trailing ink is drawn into the gap that follows it.

Tested with 321 assertions in a real browser against pages 1, 42, 48, 176, 582 and 604 — the opening spread, a rubʿ rosette, a 15-fragment ayah, a sajdah, a juz opening and 3 banners on one page — plus a real mouse drag across a line break, Ctrl+C, hover, a click in a 6.96 px gap, and a window resize.

Two profiles

The same page is emitted two ways. Use production: one <g class="word"> per word, every mark its own path. Dev adds a <g class="ligature"> layer and a legacy invisible polygon per ayah, and those two are the whole difference. Both render identically and carry every attribute in the reference below. Tell them apart in one line:

The ligature layer is a rendering run, not a spelling, and it is not a reliable letter segmentation: 156 words spell fewer letters in it than they actually have. Take the text of record from data-rasm-uthmani on the word, or from the rasm form in the page's sidecar. The page at the top of this document is the production profile.

Two levels of decomposition

Every page's root <svg> carries data-decomposition, with two possible values. word is what this page has been showing: words, ligatures and named marks are all addressable. ayah is page ink with ayah polygons and end-marks and nothing below the ayah — no g.word, no data-word-key, no named marks.

Hafs — the corpus described here — is word. Warsh, Qālūn, al-Dūrī and Shuʿba are ayah today. Read the attribute before writing a word-level selector. On an ayah page such a selector is not wrong, it simply matches nothing.

Versioning

Pin to a tag, because a versioned URL is immutable. The contract:

  • patch — path data or mark labels corrected, no attribute added or removed.
  • minor — attributes or files added, nothing removed or renamed.
  • major — anything removed or renamed. The format specification carries the same major.

Browser support

Plain SVG and plain DOM. Every snippet on this page uses querySelectorAll, dataset, closest, getBBox and getScreenCTM, all universally available for a decade. Nothing here needs a framework, a canvas, a worker or a polyfill.

Known limits

  • No <text> elements. All ink is paths, so browser find-in-page, native text selection and copy of the Quranic text do not work. Search the search form in index/by-page/NNN.json, or an index built from it. This is inherent to rendering real calligraphy as paths.
  • No accessibility metadata in the shipped files yet. No <title>, no role, no lang. The ingredients are all there — the snippet in Hover a word, see what it means makes a page readable — but it is not shipped in the files.
  • No letter-level decomposition. Nothing says where one Arabic letter ends and the next begins, so tajwid rules expressed as character ranges cannot be mapped to ink. What is already a named mark can be coloured today.
  • Counting mark paths is not counting signs. Two slash strokes drawn touching share one path, and one sign in the corpus emits as two paths. The format specification documents each site.
  • Two pages break the uniform layout. Pages 1 and 2 are the opening spread: a different viewBox, a different page matrix, 8 lines, and 12 decorative rosettes that carry no ayah. Read the attributes rather than assuming.
  • The scope is the printed page and what is on it. These files carry the mushaf's own metadata: surah, ayah, word, line, page, the juz, hizb, rubʿ and nisf divisions, and every named mark. Translation, tafsir, audio, word timings, transliteration and the ruku and manzil divisions are your own data, and they join straight on, because data-word-key and data-ayah-key are the keys those datasets already use.

Reading which mushaf a file is

9 attributes sit on every page's root <svg>, so a file that arrives on its own still says what it is. Two of them are easy to get wrong.

The directory name is the riwayah, not the qiraah. A qiraah is a reading and a riwayah is one transmission of it. data-qiraah="asim" names the reading of ʿĀṣim, and data-riwayah="hafs" names Hafs's transmission of that reading. Hafs and Shuʿbah are both transmissions of the same qiraah, so "hafs" alone identifies a rawi rather than a reading.

data-ayah-total="6236" is a Hafs fact, not a Quran fact. It follows the Kufi numbering system, which is what this print sets. Other numbering systems divide the same revealed text differently, and Nāfiʿ's Madani count gives 6,214. Read the total off the page rather than hardcoding it.

Never key on data-element-id or data-sig. Both appear on paths in both profiles, and both are review instruments. data-element-id is not stable across builds, and data-sig is a shape signature rather than an identity: 98 signatures serve more than one mark name.
