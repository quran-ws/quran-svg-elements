The mushaf, page by page, as files you can build with

What this is. The 604 pages of the Madinah Mushaf, as SVG files — one file per printed page. Each page looks exactly like the print it came from. Everything on it is a real element, so you can click a word and know which word it is, highlight an ayah, search for a phrase, link straight to 2:255, or change the colour of the vowel marks.

Why you would want it. If you are building a Quran app or site you normally pick between two bad options. A picture of the page looks right, but nothing on it can be selected, searched or linked. Text set in a font is alive, but it is not this print, and you have to rebuild the line breaks page by page so a reader still recognises the page they memorised from. These files give you both at once.

The guarantee

Every one of the 604 pages renders identically to the source artwork. Taking a page apart into ayahs, words and marks changes nothing about what is drawn.

That is checked two ways on every page, on every change, as a gate that blocks a release:

  • Contour conservation — the multiset of drawn contours in the output is identical to the source. Nothing added, nothing removed, nothing duplicated. This catches what a picture cannot show, such as a mark drawn twice in the same place.
  • Raster comparison against the source artwork, so nothing has moved. Rendered 1400 px wide, re-verified at 2200 px, tolerance 24/255, with a 10 px seam allowance that sits inside a measured empty band: anti-aliasing seams measure 1–3 px, the smallest real defect ever found measured over 100.

This is a statement about the ink: what is drawn, and where. How the ink is named — which stroke is a kasra, which word owns which mark — is a separate matter resting on separate evidence, and is not covered by this guarantee.

How to use it

Every snippet below is editable and runs for real. Change the code and the result updates as you type; Ctrl/⌘+Enter runs it immediately, and Reset restores both the snippet and an untouched copy of the page. Each editor has its own copy of the file, so one section cannot disturb another. Inside a snippet you have svg (that section's page), stage (the paper it sits on), out(html) and log(…) to report, and H — a few helpers defined on this page: H.band, H.fold, H.crop, H.getPage, H.toRoot. Everything else is plain DOM.

fetch → DOMParser → querySelectorAll

1 · Fetch a page and look inside it

There is no SDK. A page is an ordinary SVG file with a fixed viewBox. Parse it and it answers questions. This really fetches page 3 over the network — change the page number, or the ayah, and run it again.

Words inside a line are in reading order, right to left, on all 8,820 lines of the mushaf that hold words, so document order is reading order. Do not sort by geometry; bounding boxes overlap, because a mark may legitimately be drawn over its neighbour.

svg.querySelectorAll('g.ayah[data-aid="2:255"]')

2 · Highlight an ayah — and the one thing everybody gets wrong

An ayah is emitted once per printed line, so it is several sibling nodes and there is no single node that "is" the ayah. 6,236 ayahs are emitted as 13,489 fragments; 4,455 of them have more than one. Change querySelectorAll to querySelector in the editor and watch five sixths of Ayat al-Kursi stop being highlighted, without anything throwing.

Each fragment carries data-part and data-ayah-parts, and all 13,489 of them carry data-marker pointing at the id of their own medallion on the same page. No ayah spans two pages, so if you loaded the right page you will always find all N. Never use firstElementChild of one fragment to find the ayah's first word — use data-wid order across all fragments. Deep links work on the page at the top of this document: #2:254, #2:255.

g.word path { stroke: transparent; pointer-events: all }

3 · Make a tap in the gap still hit the ayah

Hit-testing runs against the ink, and the ink is calligraphy: thin strokes with white space between the words. A finger landing between two words of one ayah hits nothing. The fix is one CSS rule and it changes no pixel — a transparent stroke behind the fill is still hit-tested, and paints nothing. Click the line below with the halo at 0, hunt for a gap, then set HALO to 1.6 and click the same spots again.

This replaces the invisible per-ayah polygon that older mushaf SVGs use as a hit layer, and it is more accurate than one: where two ayahs share a printed line the real boundary is jagged — letters interleave, marks overhang — so a rectangular polygon paints part of the wrong ayah or misses ink of its own. Walking up from the word cannot be wrong: the ayah's ink is its words. Above about 2.5 units the halos start stealing each other's gaps.

getBBox() per word, unioned per printed line

4 · The coloured stripe behind an ayah

The other thing a polygon layer was for: a highlight band. Compute it instead. Union the word boxes, one box per printed line the ayah occupies, and paint a rect behind the ink. No <g> inside a word carries a transform, so word.getBBox() is directly usable. The whole function is in the editor — change the padding, the colour or the ayah and it redraws.

Put the alpha on the layer, not on the rects

Arabic ink overruns its line: ل and ك reach up into the line above, ج and ي reach down. Consecutive bands therefore overlap a little. If each rect were translucent, the overlap would double its alpha and draw a dark seam at the join.

Give the rects an opaque fill and put one opacity on the group. The layer composites flat first and the alpha is applied once, so any overlap is a single even tone. Because the highlight is a layer behind the ink rather than a colour on it, the print is still the print, which matters given the guarantee above.

data-search — and why not data-rasm

5 · Search, and land on the ink

There are no <text> nodes here — all ink is paths, so browser find-in-page cannot work. Search goes through data-search on the word groups. Edit the query in the snippet, or swap data-search for data-rasm and watch the hits vanish.

The trap — use data-search, never data-rasm

data-rasm is the skeleton of the uthmani spelling, which is what the page draws. The uthmani spelling writes several long vowels as combining marks, and stripping the marks deletes them outright. Nobody types the result. Measured over all 77,432 words:

querymatches in data-rasmmatches in data-search
الله22,555
الذين0999
درجات014

ٱللَّهُ has an alef wasla (U+0671) where a keyboard produces a plain alef, so data-rasm is ٱلله and never matches. دَرَجَٰتࣲ carries a dagger alef (U+0670), which is a mark, so the rasm is درجت with no alef at all. data-search is the skeleton of the modern (data-imlaei) spelling and has neither problem. Use data-rasm for what it is for: matching text against the shapes actually drawn on the page.

Nothing is folded for you, deliberately. ا أ إ آ stay distinct, so do ى/ي and ة/ه. If your users expect a forgiving search, fold on your side and keep the stored value as written. The snippet above does the fold; delete it and see what happens.

The same thing across all 604 pages

An index built from the same attribute: 77,432 rows, 2.0 MiB raw and 473 KiB gzipped, fetched on your first search rather than on page load. A hit gives a data-wid and a page number; the demo then fetches that one page and marks it.

6 · Read a word

Every word group carries its text in five forms and its key; every path says what kind of ink it is and, if it is a mark, which mark. The snippet installs the listener — hover the page beside it, then change what the readout reports.

Two things a drawing cannot tell you, and the attributes settle both. fatha and kasra are the same stroke, named by where it sits; you cannot recover the name from the outline. And a hamza that is a diacritic and a hamza that is a letter of the word are identical ink — data-kind is what separates them. A mark can also be drawn outside its own word: the tanween of a word-final ة floats into the gap toward the next word. Never assign a mark to a word by nearest ink or by bounding box; the enclosing group is the answer.

data-wid === quran.com's word key

7 · Pin a translation to a word

data-wid is surah:ayah:word, 1-based — the same key the quran.com API, word-by-word translation sets, morphology data and quran-align's recitation timings already use. Your existing word-keyed data joins to this ink with no mapping table. The snippet fetches a 5 KB gloss file and hangs a native SVG <title> on every word; rest the cursor on the page and the browser shows it.

Word-by-word English and transliteration here come from quran.com. They are third-party data, shipped separately from the SVGs and attributed to their source. They are not part of this corpus, and neither are translations, tafsir or audio — but they all join on the same key.

path[data-kind] · path[data-mark] · path[data-mark-family]

8 · Style or hide marks by meaning

Every ink path in the mushaf is fill="#231f20", and a CSS rule beats a presentation attribute, so recolouring by meaning needs no re-export and no second file. First, the same printed line three ways.

as printed

vowel marks hidden

every mark hidden

Hide the vowels. Never hide the dots.

Every diacritic, every letter dot and every pause sign is a data-kind="mark" path, so path[data-kind="mark"]{display:none} takes all three away at once — the third specimen above. That is not undiacritised text. The dots are the letters: ب ت ث differ by nothing else, and hiding them destroys letter identity. The waqf signs are recitation information, not vocalisation.

The nine vowel marks carry data-mark-family="diacritic" — fatha, kasra, damma, sukun, shadda, maddah and the three tanween — so hiding exactly those is one selector, and everything else stays where it belongs. That is the second specimen, and it is what a reader mode or a memorisation aid wants.

svg path { fill: … }

9 · Theme the page

Every ink path in the whole mushaf is the same colour, #231f20. One rule changes all of it. That gives you a real dark mode, a high-contrast print sheet, or a page that matches your own palette — and none of it touches the geometry, so the print stays the print. A page image cannot do any of this; inverting a photograph is not a dark mode.

Set the fill. Do not rasterise the page and filter it: a CSS filter: invert() over an image gives you grey paper and muddy ink, and it fights every other colour on the page. Here the ink and the ground are independent, because they always were.

g.ayah-marker > path[data-kind="ayah-marker-ornament" | "ayah-number"]

10 · Restyle or swap the ayah end-marker

The medallion at the end of an ayah is <g class="ayah-marker" id="mk-2-255"> holding two paths: the ornament ring, and the printed numeral. They are separate elements — which is the whole reason you can restyle the furniture without touching the number. Recolour the ring on its own, hide it and keep the numeral, scale the whole medallion, replace the ring with a shape of your own, or drop the markers entirely for a plain reading view.

The numeral is the print's own drawing of the number, not a font rendering of it, so it stays exactly as printed however you dress the ring around it. On pages 1 and 2 there are also 12 decorative rosettes with no ayah at all — the frame of the opening spread — so select g.ayah-marker[data-aid] when you mean the real ones.

g.line { transform: translate(0, …) }

11 · Open up the leading

A mushaf page is fixed geometry and cannot reflow. But every printed line is its own group, so the lines can be moved apart without touching a single glyph. That is a large-print or low-vision reading mode on a page that still has the print's own line breaks — and it is something a page image cannot offer at all.

Whole lines move; nothing is scaled, stretched or re-set. The words inside a line keep their exact printed positions relative to each other, so the page you are reading is still the page you memorised from, just further apart. The snippet grows the viewBox to match, so nothing is cropped.

clone → filter → getBBox() → new viewBox

12 · Any crop is a component

One word for a vocabulary card, a run of words for a quotation, one ayah for a citation, one line for a header. Same twelve-line function, different filter. The result is a standalone SVG you can drop into a slide, a video or a print layout at any size. Edit the filter.

Read the viewBox off the file rather than hardcoding 0 0 345 550. 602 pages use it, but pages 1 and 2 do not: they are the opening spread, with a different viewBox, a different page matrix and 8 printed lines instead of 15.

data-sid · data-juz-start · data-hizb-start · data-rub-start

13 · Metadata without a database, and a reader in thirty lines

You do not need to bundle a Quran metadata package to build a reader chrome. Open the page and read it off. The snippet runs on whichever page the reader is showing — turn pages with the buttons or the ← → keys and it re-runs on the new one. Try 582 (juz 30 opens), 1 (the opening spread), 42 (a rubʿ rosette), 176 (a sajdah).

Pages are fetched one at a time, on demand — 794 KiB raw, 197 KiB over the wire gzipped, which is the same technique any consumer should use. This document inlines exactly one page and fetches everything else.

Two profiles

The same page is emitted two ways. Production is what you want: one <g class="word"> per word, every mark its own path. Dev adds a <g class="ligature"> layer and a legacy invisible polygon per ayah. They render identically. Tell them apart in one line:

The ligature layer is a rendering run, not a spelling. It is not a reliable letter segmentation — 156 words spell fewer letters in it than they actually have — so use data-uthmani / data-rasm on the word as the text of record. The page inlined at the top of this document is the production profile.

Versioning

Pin to a tag; a versioned URL is immutable. The contract: patch — path data or mark labels corrected, no attribute added or removed; minor — attributes or files added, nothing removed or renamed; major — anything removed or renamed, and the format spec carries the same major.

Browser support

Plain SVG and plain DOM. Every snippet on this page uses querySelectorAll, dataset, closest, getBBox and getScreenCTM — all universally available for a decade. Nothing here needs a framework, a canvas, a worker or a polyfill.

Honest limits

  • No <text> elements, ever. All ink is paths, so browser find-in-page, native text selection and copy of the Quranic text do not work. Search goes through data-search or an index built from it. This is inherent to a paths-only rendering of real calligraphy.
  • No accessibility metadata in the shipped files yet. No <title>, no role, no lang. The ingredients are all there — the snippet in §7 makes a page readable — but it is not baked in, and pretending otherwise would be worse than saying so.
  • No letter-level decomposition. Nothing says where one Arabic letter ends and the next begins, so tajwid rules expressed as character ranges cannot be mapped to ink. What is already a named mark can be coloured today.
  • Counting mark paths is not counting signs. Two slash strokes drawn touching share one path; one sign in the corpus emits as two paths. The difference is small and documented site by site in the format spec.
  • Two pages break the uniform layout. Pages 1 and 2 are the opening spread: a different viewBox, a different page matrix, 8 lines, and 12 decorative rosettes that carry no ayah. Read the attributes rather than assuming.
  • No audio, no translation, no tafsir, no word timings. Out of scope, and joinable — data-wid and data-aid are the keys those datasets already use.
