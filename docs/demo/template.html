The mushaf, page by page, as files you can build with

What this is. The 604 pages of the Madinah Mushaf, as SVG files — one file per printed page. Each page looks exactly like the print it came from. Everything on it is a real element, so you can click a word and know which word it is, highlight an ayah, search for a phrase, link straight to 2:255, or change the colour of the vowel marks.

Why you would want it. If you are building a Quran app or site you normally pick between two bad options. A picture of the page looks right, but nothing on it can be selected, searched or linked. Text set in a font is alive, but it is not this print, and you have to rebuild the line breaks page by page so a reader still recognises the page they memorised from. These files give you both at once.

It also replaces your Quran metadata database. Most apps ship page images alongside a database that says what is on them. Here that information is on the elements themselves — the surah's number, its name in Arabic, Latin and English, where it was revealed and how many ayahs it has; the ayah key 2:255 and which parts of it fall on this page; the word key 2:255:4 with its rasm_uthmani text, and its other four forms in the page's sidecar; juz, hizb, rubʿ and nisf and where each begins; the page and line number; and every mark named, sajdah signs and iqlab meems included. So "ayah 2:255 is on page 42, line 3" is a CSS selector rather than a query — and because the geometry is in the same file, you also get the one thing a database cannot give you: where each of those sits on the page.

The guarantee

Every one of the 604 pages renders identically to the source artwork. Taking a page apart into ayahs, words and marks changes nothing about what is drawn.

That is checked two ways on every page, on every change, as a gate that blocks a release:

  • Contour conservation — the multiset of drawn contours in the output is identical to the source. Nothing added, nothing removed, nothing duplicated. This catches what a picture cannot show, such as a mark drawn twice in the same place.
  • Raster comparison against the source artwork, so nothing has moved. Rendered 1400 px wide, re-verified at 2200 px, tolerance 24/255, with a 10 px seam allowance that sits inside a measured empty band: anti-aliasing seams measure 1–3 px, the smallest real defect ever found measured over 100.

This is a statement about the ink: what is drawn, and where. How the ink is named — which stroke is a kasrah, which word owns which mark — is a separate matter resting on separate evidence, and is not covered by this guarantee.

What is on this page

Every section below is a live, editable example running against a real page of the mushaf. Change the code and the result changes with it.

How to use it

Every snippet below is editable and runs for real. Change the code and the result updates as you type; Ctrl/⌘+Enter runs it immediately, and Reset restores both the snippet and an untouched copy of the page. Each editor has its own copy of the file, so one section cannot disturb another. Inside a snippet you have svg (that section's page), stage (the paper it sits on), out(html) and log(…) to report, H — a few helpers defined on this page: H.band, H.fold, H.crop, H.getPage, H.toRoot — and signal, an AbortSignal that fires when the snippet is re-run, so a listener or an observer you attach outside the page is cleaned up for you. Everything else is plain DOM.

fetch → DOMParser → querySelectorAll

1 · Fetch a page and look inside it

There is no SDK. A page is an ordinary SVG file with a fixed viewBox. Parse it and it answers questions. This really fetches page 3 over the network — change the page number, or the ayah, and run it again.

Words inside a line are in reading order, right to left, on all 8,820 lines of the mushaf that hold words, so document order is reading order. Do not sort by geometry; bounding boxes overlap, because a mark may legitimately be drawn over its neighbour.

svg.querySelectorAll('g.ayah-fragment[data-ayah-key="2:255"]')

2 · Highlight an ayah — and the one thing everybody gets wrong

An ayah is emitted once per printed line, so it is several sibling nodes and there is no single node that "is" the ayah. 6,236 ayahs are emitted as 13,489 fragments; 4,455 of them have more than one. Change querySelectorAll to querySelector in the editor and watch five sixths of Ayahs al-Kursi stop being highlighted, without anything throwing.

Each fragment carries data-fragment and data-ayah-fragments, and all 13,489 of them carry data-mark pointing at the id of their own medallion on the same page. No ayah spans two pages, so if you loaded the right page you will always find all N. Never use firstElementChild of one fragment to find the ayah's first word — use data-word-key order across all fragments. Deep links work on the page at the top of this document: #2:254, #2:255.

g.word path { stroke: transparent; pointer-events: all }

3 · Make a tap in the gap still hit the ayah

Hit-testing runs against the ink, and the ink is calligraphy: thin strokes with white space between the words. A finger landing between two words of one ayah hits nothing. The fix is one CSS rule and it changes no pixel — a transparent stroke behind the fill is still hit-tested, and paints nothing. Click the line below with the halo at 0, hunt for a gap, then set HALO to 1.6 and click the same spots again.

This replaces the invisible per-ayah polygon that older mushaf SVGs use as a hit layer, and it is more accurate than one: where two ayahs share a printed line the real boundary is jagged — letters interleave, marks overhang — so a rectangular polygon paints part of the wrong ayah or misses ink of its own. Walking up from the word cannot be wrong: the ayah's ink is its words. Above about 2.5 units the halos start stealing each other's gaps.

getBBox() per word, unioned per printed line

4 · The coloured stripe behind an ayah

The other thing a polygon layer was for: a highlight band. Compute it instead. Union the word boxes, one box per printed line the ayah occupies, and paint them behind the ink as one polygon — a single <path> with a subpath per line. No <g> inside a word carries a transform, so word.getBBox() is directly usable. The whole function is in the editor — change the padding, the colour or the ayah and it redraws.

Draw one polygon, not one rectangle per line

Arabic ink overruns its line: ل and ك reach up into the line above, ج and ي reach down. So the band for an ayah is one rectangle per printed line, and those rectangles meet or overlap.

Do not emit them as separate <rect>s. Two abutting antialiased edges do not add up to opaque, so every join shows a pale hairline and a six-line ayah reads as six stripes rather than one highlight. Make each line a subpath of a single <path>, wind them all the same direction, and overlap them vertically by a fraction of a unit. One element, one flat region, no seams.

Set fill-rule explicitly; never inherit it. nonzero is what makes overlapping subpaths union instead of cancel — which is why the overlap costs nothing. The page's own ink is evenodd, where overlapping contours inside one path cancel: inherit that and every overlap becomes a hole. The alpha then goes once, on the group. Because the highlight is a layer behind the ink rather than a colour on it, the print is still the print, which matters given the guarantee above.

the search form — and why not rasm

5 · Search, and land on the ink

There are no <text> nodes here — all ink is paths, so browser find-in-page cannot work. Search goes through the search form, which ships once per page in index/by-page/NNN.json (dev-profile pages also carry it inline as data-search). Edit the query in the snippet, or swap search for rasm and watch the hits vanish.

The trap — use search, never rasm

In production both are fields of the page's sidecar, index/by-page/NNN.json; only the dev profile carries them inline as attributes. rasm is the skeleton of the rasm_uthmani spelling, which is what the page draws. The rasm_uthmani spelling writes several long vowels as combining marks, and stripping the marks deletes them outright. Nobody types the result. Measured over all 77,432 words:

ٱللَّهُ has an alef hamzat_al_wasl (U+0671) where a keyboard produces a plain alef, so rasm is ٱلله and never matches. دَرَجَٰتࣲ carries a dagger alef (U+0670), which is a mark, so the rasm is درجت with no alef at all. search is the skeleton of the modern (rasm_imlai) spelling and has neither problem. Use rasm for what it is for: matching text against the shapes actually drawn on the page.

Nothing is folded for you, deliberately. ا أ إ آ stay distinct, so do ى/ي and ة/ه. If your users expect a forgiving search, fold on your side and keep the stored value as written. The snippet above does the fold; delete it and see what happens.

The same thing across all 604 pages

6 · Read a word

Every word group carries its key and its rasm_uthmani text; the other four forms come from the page's sidecar, index/by-page/NNN.json. Every path says what kind of ink it is and, if it is a mark, which mark. The snippet installs the listener — hover the page beside it, then change what the readout reports.

Two things a drawing cannot tell you, and the attributes settle both. fathah and kasrah are the same stroke, named by where it sits; you cannot recover the name from the outline. And a hamzah that is a diacritic and a hamzah that is a letter of the word are identical ink — data-kind is what separates them. A mark can also be drawn outside its own word: the tanwin of a word-final ة floats into the gap toward the next word. Never assign a mark to a word by nearest ink or by bounding box; the enclosing group is the answer.

one invisible <span> per g.word, over the ink

7 · Drag across the page and copy real text

Drag over the page with the mouse, then Ctrl/⌘+C, or right-click and Copy. You get the Quranic text. There are no <text> elements in the file, so native selection has nothing to grab — the fix is to overlay a text layer, one absolutely-positioned span per word, carrying the real Unicode and painted with color: transparent on top of the word's own rendered box. It is the same trick PDF.js uses, it needs no library, and the ink underneath is untouched.

Five things that go wrong, and what to do instead

  • getBBox() is the wrong measurement. It reports a group's own user-space coordinates and ignores every transform above it, which puts line 1 near the bottom of the page. Use getBoundingClientRect() on the word and subtract the layer's own rect — it is already through the whole transform chain. Worst residual misalignment across all 127 words of page 3 is then 0.016 px.
  • Caret placement inside a span uses the fallback font's advances, which have nothing to do with the ink, so a drag starting mid-word cuts it at an arbitrary letter. Snap the range out to whole spans on mouseup. Word granularity is what a mushaf reader wants anyway.
  • Do not size a span to its LINE's box. A line group's rect includes the ascenders and descenders that overrun into its neighbours, so the bands overlap and darken. Per-word boxes look right.
  • Do not put a newline inside a span, and do not use a separate zero-size break span. The first makes that span two text lines tall, so its band spills onto the line below; the second has its newline collapsed away and never reaches the clipboard. Build the payload yourself in a copy handler instead.
  • A mousedown on already-selected text does not start a new selection. It starts a native drag-and-drop of that text, and the old selection sits frozen for the whole gesture. The second drag therefore appears to do nothing — and it bites hardest exactly when the user tries again, because the words under the pointer are the ones they just selected. It looks like a bug in your geometry and it is not. Clear the selection on mousedown and refuse dragstart; two lines, and every drag starts fresh. This section and §3, §10 and §11 now share one layer and one box size — full-height boxes that meet their neighbours, so there are no dead zones and the first and last word of a range need no deliberate aim.

Why building the payload yourself is the good part

Because the text is looked up from data-word-key rather than serialised out of the layer, the same drag can yield different text. Quote it as the print sets it, take the modern spelling, or take the bare form to paste into a search box. Change the WHICH line in the editor, or use the selector in the toolbar.

Neither a page image nor text set in a font can offer this. An image has nothing to select; a font gives you one spelling, the one it was set in. Here the selection is a set of word ids, and the spelling is chosen at copy time.

What is verified, and what is not. The copy event and the payload it produces are tested: a real mouse drag across a line break, the highlighted band and the copied word set agreeing at both boundaries, and the mushaf's own line break preserved as a newline. The handoff to the operating system clipboard was not testable in the headless browser used here — it has no clipboard backing — so that last step is the one part of this section proven only by hand.

g.word { fill: … } — one property, one word

8 · Reveal the page word by word

Every word on the page starts light grey. The reading position is full ink, and it advances, each word fading in as it is reached. This is what a memorisation prompt, a reading-along view and a "you are here" indicator all reduce to, and once words are addressable all three are one property away. A page image cannot do it at all — recolouring one word at a time needs per-word ink.

Set the colour on the group, not on 1,000 paths

Every ink path ships fill="#231f20" as a presentation attribute, so a <g>'s inherited fill will not reach it on its own. A CSS rule beats a presentation attribute, so one rule hands each path back to its group — and then recolouring a whole word is setting one property on one element per tick, whatever the word is made of.

Measured on this page: 147 words over 1,061 paths, and the transition is on fill. It stays smooth because a tick touches one element, not a thousand — the browser does the interpolation. If you ever need it cheaper, transition opacity on the group instead.

The schedule is pluggable, and it is not audio

The advance is driven by a schedule(i) function returning the millisecond at which word i lights. Today that is a constant tempo. Swap in an array of per-word start times from a recitation aligner and the same loop follows a recitation — same code, different source.

Nothing here is synced to a recitation. These files carry no audio and no word timings, and the animation you are watching is a metronome. The reason it is worth showing anyway is that data-word-key is surah:ayah:word — the same key word-level timing datasets are published under — so the join needs no mapping table.

Word order is document order: right to left within a printed line, lines top to bottom, correct on all 8,820 lines of the mushaf that hold words. The loop below never sorts by geometry, and it does not need to.

word_number → the third part of data-word-key

9 · Follow a recitation, word by word

The same grey-to-ink mechanism as §8, with the tempo replaced by real per-word timings. Press play: the highlight follows the recitation because quran.com publishes word timings under the same key this page uses — word_number is 1-based within the ayah, which is exactly the third component of data-word-key. No mapping table, no alignment step.

Check the word counts before you trust the numbering

Two decompositions can disagree about how many words an ayah has. On page 254, 13:37 is 19 words to quran.com and 20 in this print, which sets بَعْدَ مَا as two. Consume the timings blindly and the highlight drifts by one word to the end of that ayah — and drift looks like the geometry is wrong, which is worse than no highlight at all.

Three lines fix it: compare the highest word_number against your own count for that ayah, and fall back to highlighting the ayah whole when they differ. Measured against this build: pages 1, 3, 42, 582 and 604 agree exactly across 67 ayahs; page 254 has the one mismatch. The lab prints the check either way, so you can see it pass.

What this section is, and is not

This streams audio and timings from quran.com for one page, to demonstrate the join between word_number and data-word-key. Recitation: Mohamed Siddiq al-Minshawi, Murattal.

The SVGs carry no audio and no word timings, and none is planned. Nothing about recitation is in the bundle, the format specification or the attribute tables. The audio and the timings are quran.com's, and their terms apply to them — not to these files, and not the other way round.

It is also the one part of this page that talks to the network beyond fetching mushaf pages. If the API is unreachable the section falls back to a 2 KB cached copy of this page's timings and says so.

One MP3 per ayah, not per page, and each ayah's times are relative to its own file — so the player sequences four files across page 42 and resets the clock at each boundary, preloading the next before the current ends. The highlight is driven from currentTime on every frame, never from a chain of timeouts: a chain drifts against the audio, and drift is the failure that makes the geometry look wrong.

data-word-key === quran.com's word key

10 · Hover a word, see what it means

Move the pointer over any word on the page and its meaning appears. Tap works on touch, and the words are focusable so Tab and the arrow keys do too. data-word-key is surah:ayah:word, 1-based — the same key the quran.com API, word-by-word translation sets, morphology data and recitation timings already use, so a 5 KB file of glosses joins to this ink with no mapping table.

What you see here is an example, not a feature. The gloss is word-by-word translation English from quran.com, used because it is open data anyone can check; the point is the join, not the language. Put a tafsir, a grammar tag, a vocabulary card or any per-word data you already have in its place and the same three lines still run — and none of it is possible on a page image. These files ship no translations.

Word-by-word-translation English and transliteration here come from quran.com. They are third-party data, shipped separately from the SVGs and attributed to their source. They are not part of this corpus, and neither are translations, tafsir or audio — but they all join on the same key. Two implementation notes. The hit areas are transparent <rect>s inside the SVG, one per word: attaching to the paths makes the tooltip flicker as the pointer crosses the gaps between letters. And if you ever combine this with §7's HTML text layer, the layer sits above the SVG and will swallow these events — decide which one owns pointer-events rather than stacking both.

one hit layer · many capabilities

11 · All of it at once

These are not alternatives. A real reader runs several together, so here they are on one page at the same time: hover a word for its meaning, drag across it and copy real text, and a band behind the ayah you are on. Nothing here is a special case — it is the same three snippets from §7, §10 and §4, sharing one hit layer.

How they coexist

Three layers, and only one of them takes the pointer. The highlight bands sit behind the ink and the ink itself is pointer-events: none; the per-word hit layer on top is the only thing hit-testing ever reaches. Because that layer is one element per word carrying its data-word-key, selection, hover, tap and click all read from the same source instead of stacking competing overlays.

The one thing that genuinely cannot be shared is the cursor: selection wants cursor: text and a tooltip target wants cursor: help. Pick one per surface. Everything else composes.

path[data-kind] · path[data-mark] · path[data-mark-family]

12 · Style or hide marks by meaning

Every ink path in the mushaf is fill="#231f20", and a CSS rule beats a presentation attribute, so recolouring by meaning needs no re-export and no second file. First, the same printed line three ways.

as printed

vowel marks hidden

every mark hidden

Hide the vowels. Never hide the dots.

Every diacritic, every letter dot and every waqf sign is a data-kind="mark" path, so path[data-kind="mark"]{display:none} takes all three away at once — the third specimen above. That is not undiacritised text. The dots are the letters: ب ت ث differ by nothing else, and hiding them destroys letter identity. The waqf signs are recitation information, not tashkil.

The nine vowel marks carry diacritic in data-mark-family — fathah, kasrah, dammah, sukun, shaddah, maddah and the three tanwin — so hiding exactly those is one selector, and everything else stays where it belongs. That is the second specimen, and it is what a reader mode or a memorisation ayahKey wants.

data-mark-family is a space-separated token list, like class. A mark can belong to more than one family: the three tanwin are vowel marks and they are the tanwin, so they carry data-mark-family="diacritic tanwin" and must answer to both names. Match it with ~=, never =:

An exact-match selector is not merely stricter here, it is wrong: it looks like it works, because it still matches the six single-family marks, and it drops the three tanwin without an error. Every selector on this page uses ~=.

svg path { fill: … }

13 · Theme the page

Every ink path in the whole mushaf is the same colour, #231f20. One rule changes all of it. That gives you a real dark mode, a high-contrast print sheet, or a page that matches your own palette — and none of it touches the geometry, so the print stays the print. A page image cannot do any of this; inverting a photograph is not a dark mode.

Set the fill. Do not rasterise the page and filter it: a CSS filter: invert() over an image gives you grey paper and muddy ink, and it fights every other colour on the page. Here the ink and the ground are independent, because they always were.

g.ayah-mark > path[data-kind="ayah_mark_ornament" | "ayah_number"]

14 · Swap or restyle the ayah end-mark

The medallion at the end of an ayah is <g class="ayah-mark" id="mk-2-255"> holding two paths: the ornament ring, and the printed numeral. They are separate elements — which is the whole reason you can restyle the furniture without touching the number. Recolour the ring on its own, hide it and keep the numeral, scale the whole medallion, replace the ring with a shape of your own, or drop the markers entirely for a plain reading view.

The outlines are not part of this page. The designs in the picker are fetched at runtime from quranpedia/ayah-marks, which traces them from twenty type families — fifteen from Google Fonts, five from fonts.quran.ws. They carry those families' licences, which differ from one another; every marker names its own sources in that repository's collection.json. Read it before you redistribute anything. Neither this page nor the library ships a single outline, and neither states any licence terms. If the fetch fails the section says so and the printed rings stay.

The numeral is the print's own drawing of the number, not a font rendering of it, so it stays exactly as printed however you dress the ring around it. On pages 1 and 2 there are also 12 decorative rosettes with no ayah at all — the frame of the opening spread — so select g.ayah-mark[data-ayah-key] when you mean the real ones.

g.line { transform: translate(0, …) }

15 · Open up the leading, and fill a phone screen

On a phone this is not an accessibility nicety, it is the difference between using the screen and wasting it. The page is 345 × 550; a phone is far narrower for its height, so fitting the page to the width leaves about a quarter of the display empty. Spreading the lines into that space fills the screen with the same page — same line breaks, same glyph positions, nothing scaled or stretched. A page image can only zoom, which crops or distorts.

It is also a large-print and low-vision reading mode, on a page that still has the print's own line breaks. Drag the slider, or press fill a phone screen to let the snippet compute the gap from the page's own viewBox and line count.

18 · A library, if you want one

Every section above has a plain JS / library switch in its toolbar. Both versions are real, both are editable, both run, and both produce the same result. Plain JS is the default on purpose — it is the teaching, and it is the argument: these are ordinary SVG files and they need no library at all. Nothing on this page is a wrapper you must adopt.

What the library saves you is not typing, it is the traps. Every one of the callouts on this page is a bug somebody had to find first — that an ayah is several nodes, that getBBox() reports the wrong position, that a band must be one path, that a word's trailing ink is drawn into the following gap, that data-mark-family is a token list. The library has those baked in and tested.

Getting it

Zero dependencies, no build step, no framework. An ES module, or a <script> tag with everything on one global — which is what this page loads, the first time you press library in any toolbar.

core.mjs imports nothing at all, and everything else is a free function taking a page — attachSelection(page, …), mask(page, …) — precisely so a bundler can drop what you do not use.

Three rules it keeps everywhere

  • Nothing mutates a page you did not hand it. MushafPage.load() and page.clone() give you a page you own; new MushafPage(el) wraps an element without cloning, so a later call changes your element — which is what every library snippet on this page relies on.
  • Every mutating call returns a handle with .remove() that undoes exactly what it did and nothing else. There is no global reset, and no call leaves you guessing what state you are in.
  • The shared hit layer is reference counted. Hover, click and selection all take a reference and give it back; the layer is built once and torn down when the last holder releases it. That is what lets §11 run three capabilities over one page without any of them knowing about the others.

Where it disagrees with this page, follow the library

Two places it is deliberately stricter than the plain snippets. It never selects on data-mark-family — it resolves a family to data-mark names through an embedded taxonomy, so a build that changes the attribute's vocabulary cannot break your code. And its hit testing is nearest-with-direction: a point in the gap between two words goes to the preceding one, because in this print a word's trailing ink is drawn into the gap that follows it.

It is tested with 217 assertions in a real browser against pages 1, 42, 48, 176, 582 and 604 — the opening spread, a rubʿ rosette, a fifteen-fragment ayah, a sajdah, a juz opening and three banners on one page — plus a genuine mouse drag across a line break, Ctrl+C, hover, a click in a 6.96 px gap, and a window resize.

Two profiles

The same page is emitted two ways. Production is what you want: one <g class="word"> per word, every mark its own path. Dev adds a <g class="ligature"> layer and a legacy invisible polygon per ayah, and those two are the whole difference — every attribute in the reference below is in both. They render identically. Tell them apart in one line:

The ligature layer is a rendering run, not a spelling. It is not a reliable letter segmentation — 156 words spell fewer letters in it than they actually have — so use data-rasm-uthmani on the word, or the rasm form in the page's sidecar, as the text of record. The page at the top of this document is shown in the production profile.

Two levels of decomposition

Every page's root <svg> carries data-decomposition, and it has two values. word means what this whole page has been showing: words, ligatures and named marks are addressable. ayah means page ink with ayah polygons and end-marks and nothing below the ayah — no g.word, no data-word-key, no named marks.

Hafs — the corpus described here — is word. Warsh, Qālūn, al-Dūrī and Shuʿba are ayah today. Read the attribute before writing a word-level selector; on an ayah page the selector is not wrong, it simply matches nothing.

Versioning

Pin to a tag; a versioned URL is immutable. The contract: patch — path data or mark labels corrected, no attribute added or removed; minor — attributes or files added, nothing removed or renamed; major — anything removed or renamed, and the format spec carries the same major.

Browser support

Plain SVG and plain DOM. Every snippet on this page uses querySelectorAll, dataset, closest, getBBox and getScreenCTM — all universally available for a decade. Nothing here needs a framework, a canvas, a worker or a polyfill.

Honest limits

  • No <text> elements, ever. All ink is paths, so browser find-in-page, native text selection and copy of the Quranic text do not work. Search goes through the search form in index/by-page/NNN.json or an index built from it. This is inherent to a paths-only rendering of real calligraphy.
  • No accessibility metadata in the shipped files yet. No <title>, no role, no lang. The ingredients are all there — the snippet in §10 makes a page readable — but it is not baked in, and pretending otherwise would be worse than saying so.
  • No letter-level decomposition. Nothing says where one Arabic letter ends and the next begins, so tajwid rules expressed as character ranges cannot be mapped to ink. What is already a named mark can be coloured today.
  • Counting mark paths is not counting signs. Two slash strokes drawn touching share one path; one sign in the corpus emits as two paths. The difference is small and documented site by site in the format spec.
  • Two pages break the uniform layout. Pages 1 and 2 are the opening spread: a different viewBox, a different page matrix, 8 lines, and 12 decorative rosettes that carry no ayah. Read the attributes rather than assuming.
  • Scope: the printed page and what is on it. The metadata these files carry is the mushaf's own — surah, ayah, word, line, page, the juz/hizb/rubʿ/nisf divisions, and every named mark. Translation, tafsir, audio and word timings, transliteration, and the ruku and manzil divisions are a consumer's own data, and they join straight on: data-word-key and data-ayah-key are the keys those datasets already use.

The page announces which mushaf it is

Nine attributes sit on every page's root <svg>, so a file that arrives on its own still says what it is. Two of them are easy to get wrong.

The directory name is the riwayah, not the qiraah. data-qiraah="asim" names the reading of ʿĀṣim; data-riwayah="hafs" names Hafs's transmission of it. Hafs and Shuʿbah are both transmissions of the same qiraah, so "hafs" alone does not identify a reading — it identifies a rawi.

data-ayah-total="6236" is a Hafs fact, not a Quran fact. It follows the Kufi counting system, which is what this print sets. Other counting systems divide the same revealed text differently: Nāfiʿ's Madani count gives 6,214. A total is a property of a counting tradition, so read it off the page rather than hardcoding it.

data-element-id and data-sig also appear on paths, in both profiles. They are review instruments: data-element-id is not stable across builds and data-sig is a shape signature, not an identity — 98 signatures serve more than one mark name. Never key on either.
